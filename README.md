# DigitalBots Management

DigitalBots is a central-server client and revenue management suite with a separate Windows desktop shell. The web app, desktop app and API use the same MySQL database through one central backend.

## Important architecture

- **Main server:** Node.js + Express + MySQL/MariaDB. This is the source of truth for all client, subscription, payment and security records.
- **Web app:** custom, dependency-light HTML/CSS/JavaScript dashboard served by the main server.
- **Windows desktop:** Tauri 2 shell. The first launch asks for the main server HTTPS address; it does not create a private/local database.
- **Database:** `digitalbotsclients`. HeidiSQL is an optional SQL client; it is not the MySQL server.

The frontend is intentionally shipped as static assets instead of a large frontend runtime. This keeps the interface lightweight and makes it possible to reuse the exact same UI in the hosted web server and Tauri shell.

## What is implemented

- Initial administrator setup (`digitalbots`) protected by a separate one-time server setup key; the administrator password is chosen privately at first run and stored as a bcrypt hash.
- Server-backed sessions, CSRF token checks, login rate limits and configurable 5–10 hour idle expiry (default 6 hours).
- Initial trusted IP registration, pending unknown-IP approvals, approve/reject actions, trust revocation and login history.
- Client create/list/search/filter/edit/archive (archiving preserves payment and subscription history).
- Subscription records with Basic, Premium and Business plans; 1 Month, 3 Months, 6 Months, 1 Year, Lifetime and Custom terms.
- Subscription history and extension records.
- Individual payment records; paid minus refunded payments are counted as received revenue; pending amounts are shown separately.
- Dashboard summary, recent activity, recent payments and revenue/plan charts.
- Discord integration module for guild `1569256802179354646` and invite `https://discord.gg/cwAcrz7zeH`. The bot token and webhook live only on the central server.
- CSV client/payment exports, light/dark theme, appearance preferences, password change, timeout and plan-price settings.
- Docker deployment templates, HTTPS reverse-proxy example, migration script and Windows build pipeline.

## Quick local server setup

Requirements: Node.js 22.12+ and MySQL 8 / MariaDB running.

1. Copy `.env.example` to `.env`.
2. Set `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, a random `SESSION_SECRET` (32+ characters), and a separate random `INITIAL_SETUP_KEY` (32+ characters). Generate secrets with `openssl rand -hex 32`.
3. Create a MySQL user that can create/use the `digitalbotsclients` database, or create the database first and grant access.
4. Run `npm install` from the project root.
5. Run `npm run build:web`.
6. Run `npm run db:migrate`.
7. Run `npm start`.
8. Visit `http://127.0.0.1:6767/desktop6767`, enter the `INITIAL_SETUP_KEY` from the server environment, and create the `digitalbots` administrator password.

The initial setup registers the network address used during that setup as the first trusted IP. Keep the one-time setup key in your private server environment; do not send it in Discord or commit it to source control.

See `docs/WINDOWS_BUILD.md`. The native app embeds the same static web UI and connects to the remote server API using the URL entered on first launch. The NSIS installer is per-user and includes a Desktop shortcut hook; it does not install MySQL or store server database credentials on client PCs.

## Security notes

- Do not expose port 6767 or MySQL directly to the public internet. Put the app behind an HTTPS reverse proxy or private VPN.
- For a Tauri desktop client connecting to a remote HTTPS API, set `COOKIE_SECURE=true` and `COOKIE_SAME_SITE=none` on the server and allow `tauri://localhost` (and `http://tauri.localhost` if used) in `CORS_ORIGINS`.
- Set `TRUST_PROXY=true` only when the Node service can only be reached through your trusted reverse proxy, which must replace client-supplied forwarded-IP headers.
- The old administrator password mentioned earlier in the chat should not be reused. Configure a new one during initial setup.
- IP authorization is network-address authorization; NAT and dynamic addresses mean more than one device may share an IP, and an ISP address change can require another approval.
- Database backups should be performed on the central database host. Uninstalling the desktop client does not delete server data.

## Routes

- `/desktop6767` — authenticated web application entry point.
- `/onlineconnectpc6742` — same app entry point for compatibility.
- `/api/health` — health check.

The two custom paths are not security features. Authentication and HTTPS protect the application.
